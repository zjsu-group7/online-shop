## 二、接口契约（已可交前端联调）

| 方法 | 路径 | 入参 | 说明 |
|---|---|---|---|
| POST | `/api/customer/cart` | `{productId, quantity?}` | 加购；同商品重复加入**数量累加**，不产生重复条目；缺省数量 1 |
| GET | `/api/customer/cart` | — | 列表；返回 `items / kinds / totalQuantity`，每条带 `available` 与 `unavailableReason` |
| PUT | `/api/customer/cart/{itemId}` | `{quantity}` | 改数量，`quantity >= 1`（0 返回 400，删除请走删除接口） |
| DELETE | `/api/customer/cart/{itemId}` | — | 删除单条（仅限本人条目） |
| DELETE | `/api/customer/cart` | — | 一键清空 |
| POST | `/api/customer/cart/to-favorites` | `{itemIds: [...]}` | 勾选多件转收藏，返回 `{transferred, skipped}` |
| POST | `/api/customer/favorites` | `{productId}` | 收藏，重复收藏幂等返回原条目 |
| GET | `/api/customer/favorites` | — | 收藏列表（最近收藏在前），标注口径同购物车 |
| DELETE | `/api/customer/favorites/{productId}` | — | 取消收藏（未收藏时幂等成功） |

统一响应体 `{code, message, data}`；全部端点挂在 `/api/customer/**` 下，由 `CustomerAuthInterceptor` 校验 `X-Token`，客户身份取自登录态（`@RequestAttribute`），**不接受任何 customerId 入参**。

标注字段口径（购物车与收藏一致）：

| 商场状态 | `available` | `unavailableReason` |
|---|---|---|
| 在售且可售库存 > 0 | true | null |
| 非在售（OFF_SHELF 及后续两态口径） | false | `OFF_SHELF` |
| 在售但 `availableStock() == 0`（库存被订单全部锁定） | false | `OUT_OF_STOCK` |

## 四、三个关键设计决策

**1）标注实时计算，不做定时任务**
`ProductAvailability.reasonOf(product)` 在每次列表查询时读当前 `status` 与 `availableStock()`，不落库、不记录“已通知”。好处：补货或重新上架后**下一次查询自动恢复可买**，不存在“补货了但标注还挂着”的脏状态；代价是列表查询多一次商品批量读取（`findAllById`，一次 SQL）。

**2）累加与去重交给数据库唯一约束**
加购用 `findByCustomerIdAndProductId` 先查再累加，`(customer_id, product_id)` 唯一索引兜底。已知局限：两个请求同时首次加购同一商品，可能触发唯一约束冲突（500）；单用户场景概率极低，且重试一次即成功，本轮未加锁，已记录在 §六 风险项。

**3）转收藏必须同事务**
`transferToFavorites` 标注 `@Transactional`：先校验勾选项全部属于本人（数量不符直接 400，**不部分执行**），再逐条「不存在收藏则插入 + 删除购物车条目」。避免出现“购物车删了但收藏没进”的中间态。
