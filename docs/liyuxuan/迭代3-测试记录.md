## 三、测试设计说明

1. **订单域用测试替身**：`FakeOrderGateway` 实现 `OrderGateway` 的内存五态状态机，语义与契约一致。
   这样在周琳皓的订单域合并前，本层的鉴权、隔离、参数约束就能全部验证；订单域落地后删掉该测试配置即可对真实实现回归。
2. **身份不伪造**：卖家 token 走真实 `/api/seller/login`，买家走真实 `/api/customer/register` + `/login`，
   拦截器、token 过期、request attribute 注入全部在真实路径上被验证。
3. **不污染数据库**：全部用例 `@Transactional` 回滚；测试库为内存 H2（`create-drop`）。
4. **故障注入**：`returnForeignOrder` 标志模拟「订单域误返他人订单」，专门验证本层的二次归属核对能兜住 403。

## 四、手工验证（可选，联调时使用）

订单域尚未合并，当前手工访问订单接口会得到 503，属预期降级：

```bash
# 1) 卖家登录
curl -X POST http://localhost:8080/api/seller/login \
  -H "Content-Type: application/json" \
  -d '{"username":"seller","password":"12345678"}'

# 2) 访问订单列表（订单域未合并时）
curl http://localhost:8080/api/seller/orders -H "X-Token: <token>"
# → {"code":503,"message":"订单核心域尚未接入，订单相关接口暂不可用","data":null}

# 3) 不带 token
curl -i http://localhost:8080/api/orders
# → HTTP/1.1 401
```

订单域合并后，上述第 2 步应返回订单分页列表，无需改动本域代码。

## 六、补充：联调后的第二轮验证（2026-11-18）

### 1. 新增纯单元测试 `OrderViewNormalizerTest`（9 例，不起 Spring 上下文）

守的是联调时最容易出岔子的两类事：状态码两套命名、订单域少回字段。

| 用例 | 断言 |
|---|---|
| 状态码归一 | `CUSTOMER_SUBMITTED → PENDING`、`seller_confirmed → CONFIRMED`、`READY_TO_SHIP → PACKED`，未知值返回 `null` |
| 状态文案 | 别名也能取到中文；未知码原样返回，不出现空白标签 |
| statusText 补齐 | 网关只回状态码时按字典补中文 |
| itemCount 兜底 | 回 0 时按明细行数（种数）补齐 |
| 小计兜底 | 未回小计则用 单价 × 数量；**已给出的不被覆盖** |
| available 语义 | 网关未表态时保持 `null`，不替订单域判定"无货" |
| 分页与订单号边界 | 缺省值、0/101 被拒、超 64 字符被拒、首尾空白被去掉 |
| 空页兜底 | `null` 转成第 1 页空列表 |

### 3. 联调中发现并已在本分支修复

| 问题 | 处理 |
|---|---|
| 与订单域 `dto.OrderView` 同名同包，合并即编译失败 | 本域视图改名为 `order.SellerOrderView`（只改包名类名，字段与逻辑不变） |

| 小计为空时前端金额列空白 | `OrderViewNormalizer` 兜底计算 |
| `itemCount` 语义模糊（件数 vs 种数） | 明确为**种数**，与前端"共 N 种商品"一致 |
